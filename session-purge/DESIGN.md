# 设计 v3：会话删除

> v2 交出去后我按「敌对审计」重读了一遍源码，**发现五处真问题**（其中两处会让设计自相矛盾，一处会让它撒谎）。
> 这一版是修订后的版本，§13 记录了每一处问题与修法。

---

## 1. 删除在只追加系统里的含义

> **撤销一份权威，并让所有派生在有限步内收敛到没有它。**

不是文件操作，是跨域的可达性回收。判断一个字节该不该删，问"还有没有权威引用它"，不问它叫什么。

---

## 2. 正确性模型

### 2.1 不变量

| # | 不变量 | 违反的例子 |
|---|---|---|
| **I1** | **原子可见性**：任一观察者在任一瞬间，该会话要么完整存在，要么完全不存在 | `rm -rf` 删到一半 |
| **I2** | **无悬空权威**：提交后不存在指向它的权威记录 | 行还在、点开报错 |
| **I3** | **无共享伤害**：其他会话仍引用的字节必须完好 | 删 A 把 B 的图片带走 |
| **I4** | **不可复活**：提交后没有路径能重建它的记录 | dispose 写回投影缓存 |
| **I5** | **收敛**：崩溃后重跑达到 I1 满足的状态 | 半删的目录永远留着 |
| **I6** | **可证伪**：每次删除结束都要校验，而不是假设 | 报"成功"但磁盘还在 |
| **I7** | **可补偿（有界）**：提交点之前的**持久化状态**改动要能还原；**被中断的工作不可还原，必须事先声明** | 归档清掉了置顶 |

**I7 是 v3 新增的。** 它推翻了 v2 那句轻率的"前六种错误码 = 什么都没发生"——因为 fence 阶段的 `archiveSession` 会**写归档集合、并清掉置顶**，那不是只读操作。见 §3.3。

### 2.2 假设

| # | 假设 | 不成立时 |
|---|---|---|
| A1 | 会话根与 staging 父目录同设备 | `EXDEV` → 拒绝整批，不降级 |
| A2 | POSIX 有 `flock`；Windows 无锁文件 | 后者退化为"`rename` 失败即拒绝" |
| A3 | 远端已上传文件由提供方过期回收 | 报告里点名，不假装清掉 |

### 2.3 可证明不可达

跨卷原子提交、Windows 跨进程写者、远端副本——这三件只能拒绝或声明。
**"绝对"在这里= 所有失败模式被枚举、每种有确定行为、每种有测试。**

## 3. 域与所有权

### 3.1 七个域

| 域 | 性质 | 处置 |
|---|---|---|
| 会话目录（日志+锁） | **权威** | 提交点：移出树 |
| 投影检查点 | 派生 | 提交后删；**校验时再读一次** |
| 工作区记账（成员/归档/置顶） | **权威** | 走注册表服务；**归档会清置顶，必须能还原** |
| 提醒 | **权威** | 走 Schedule 服务 |
| 附件字节 | **共享权威** | **删除时绝不碰**（见 §6） |
| 搜索索引 | 派生 | 不碰（自对账） |
| spill / 引用副本 / 临时对象 | 临时 | 顺手删；30 天自清扫兜底 |

### 3.2 谁有权删：停 → 静置 → 复检 → 驱逐 → 围栏

```
prior := { archived: registry.archivedSessionIds.includes(id),
           pinned:   registry.pinnedSessionIds.includes(id) }

停    : prior.archived
          ? ctx.parallel('workspace/session-stop', { sessionId: id })   // archive 对已归档 id 直接 return，不会停
          : registry.archiveSession(id, { stopActivity: true })

静置  : 等一个窗口，让最末的 turn/end 落盘

复检  : activity := await ctx.waterfall('workspace/session-activity', { sessionId: id }, () => [])
        activity.length > 0 → 中止（这是唯一能发现"停不下来"的手段，见 §13-②）

驱逐  : ctx.get('sessions').store?.get?.(id)?.detach?.()

围栏  : POSIX 取 session.lock 的 flock（r+ + inode 校验）证明没有别的进程在写
```

**为什么必须有"复检"**：`archiveSession({stopActivity:true})` 内部 `stopSessionActivity`
用 `try/catch` **吞掉所有 provider 失败**，只写一条 `logger.warn`，然后正常 resolve。
也就是说**它永远不会告诉我们"没停下来"**。不复检，`live-unstoppable` 这个错误码就是死代码。

**复检优先查服务，不查事件名**（§13-⑪）：`ctx.get('agents').get(id)`、`ctx.get('sessions').get(id)`
是稳定的服务缝；`workspace/session-activity` 这个 **Host 事件名**属于另一个包的内部契约，
改个名字我们就碎。所以：服务能答就用服务；事件只在 try/catch 里当补充；两者都拿不到 →
记 `unverified: ['activity']`，按"停不下来"处理（保守）。

### 3.3 补偿（I7）

fence 之后、commit 之前的任何失败或取消，必须把 §3.2 的副作用还回去：

| 做过的 | 还法 | 备注 |
|---|---|---|
| 新写入的归档位 | `unarchiveSession(id)` | 已归档的不要动 |
| 被归档清掉的置顶 | `pinSession(id)` | **必须在上一步之后**：pin 一个已归档 id 会抛 `WorkspaceArchivedSessionPinError` |
| 被杀掉的工作 | **还不了** | 这是唯一不可补偿的副作用，必须在确认框里写明"会中断正在运行的工作" |

**因此「提交前什么都没发生」这句话要改成：提交前的持久化状态改动可还原（尽力而为并事后校验），唯一确定不可还原的是被中断的运行中工作。**

补偿本身也不是无竞争的：`unarchive`/`pin` 会覆盖这期间用户的合法操作。注册表没有暴露 CAS 令牌，
所以只能「记录 → 补偿 → 回读比对」，不一致就写进审计并报 `compensation-drift`（§14-A4）。

## 4. 状态机与预写清单

### 4.1 清单

```
<stagingRoot>/<runId>/
  manifest.json                    # 意图、目标、每步进度、结果
  entries/<project>/<dirName>/     # 被移出的真实目录（链接布局则是一条链接）
```

写入：`tmp → fsync → rename`（原子）。字段：

```json
{
  "version": 2,
  "runId": "20261018T183700-3f9a",
  "startedAt": 1792345678901,
  "callerSessionId": null,
  "targets": [{ "id": "session-…", "projectDir": "--…--", "dirName": "session-…",
                "linked": false, "realTarget": null,
                "identity": "dev:ino", "sizeBytes": 12345,
                "prior": { "archived": false, "pinned": true } }],
  "steps": { "fence": "pending", "commit": "pending", "workspace": "pending",
             "cache": "pending", "schedules": "pending" },
  "outcome": null
}
```

**恢复只认清单里的 runId 目录**；没有清单的残骸一律不动，只在报告里记为"未知残骸"。

### 4.2 run 生命周期

| 阶段 | 动作 | 清单 |
|---|---|---|
| **prepare** | 索引、目标集、血缘、链接解析、prior 快照、围栏前检查 | `steps={}` |
| **fence** | 停 → 静置 → 复检 → 驱逐 → 取租约（全部目标） | `fence: done` |
| **commit** | 每个目标 `rename` 进 `entries/` | `commit: partial→done` |
| **settle** | 工作区摘除 → 检查点删除 → 提醒删除 | 逐步 `done` |
| **cleanup** | `rm -rf entries/` | `cleanup: done` |
| **verify** | §7 的断言 | `outcome: verified / failed` |

**检查点只删一次**（提交后），因为驱逐发生在提交之前——dispose 的写回已经落在提交之前，
提交后那次删除就能盖住它。v2 写"删两次"是把我自己的顺序搞混了（§13-③）。

### 4.3 全局互斥

```
flock(<stagingRoot>/.lock, LOCK_EX | LOCK_NB)   // 拿不到 → session-purge/busy
```

**键必须是 `realpath(sessionsRoot)` 派生的锁文件**，而不是"默认 staging 根"——否则两份配置指向不同
staging、同一个 sessions 根时，互斥形同虚设（§13-④）。

### 4.4 崩溃矩阵

| 崩在 | 磁盘 | 恢复（启动时自动跑一次） |
|---|---|---|
| prepare | 只有清单 | 删清单目录；若已写入归档位 → 按 §3.3 还原 |
| fence | 清单 + 归档位 | 还原归档/置顶 → 删清单目录 |
| commit 中 | 清单 + 部分条目 | 剩余目标重做 fence？**不**——已提交的继续 settle/cleanup；未提交的还原 prior 并记 failed |
| settle 中 | 全部在 entries/ | 重做剩余步骤（幂等） |
| cleanup 中 | entries/ 残片 | 直接删残片 |
| verify 后 | 清单未标 outcome | 重跑 verify |

**恢复必须先验身份（来自第二轮审计）。** 清单在 prepare 阶段记下每个目标的 `identity`（`dev:ino`；链接布局用 `lstat` 的自身身份）。恢复在动任何一条之前都要重新取一次身份：不一致 → **不碰**，记 `identity-drift` 并跳过。理由：一个已提交的目标如果在恢复前被外部改写（用户从备份拷回同名目录、或同 id 被重新创建），只按 id 认人就会把**新的**那个删掉。

**批量语义是"最终一致"，不是"全或无"**：commit 中途崩溃会留下"部分已删、部分还原"。
这是可接受的，但必须在报告里逐条说清哪些删了、哪些没删（§13-⑤）。

## 5. 提交点

### 5.1 普通目录

`<sessions>/<proj>/<dir>` → `<staging>/<runId>/entries/<proj>/<dir>`。同设备、原子。

**rename 之后必须 fsync 两个父目录**（源项目目录与 `entries/<proj>/`）：文件内容 fsync 不持久化目录项，
崩溃后可能出现「改名已返回、但名字没落盘」。这条 v3 漏了（§14-A2）。

### 5.2 链接目录

`rename` **链接本身**同样是原子的，提交点成立。cleanup 阶段：

- 目标是宿主布局（目标名 == 会话 id）→ 递归删目标，再删链接；
- 目标名任意 → 只删目标里的会话文件（`session*.jsonl*`、`session.lock`），`rmdir` 变空才成功，其余保留并记 `leftover`；
- 目标里没有任何会话文件 → **prepare 阶段就拒绝**。

**新增：链接共享检查（§13-⑥）。** 两个会话目录链接到**同一个目标**时，删一个会把另一个的字节带走——
这是和附件同类的别名危险。prepare 必须对 `realTarget` 做去重，发现共享就拒绝整批。

### 5.3 `EXDEV`

拒绝整批，不降级为就地 `rm -rf`。

## 6. 共享字节：GC 与删除彻底分离

delete **绝不碰附件**，所以 I3 从"靠算法保证"变成"结构性不可能违反"。

独立的 `gc` 操作：

- **根（marks）**：所有**可读**会话日志的 `sha256:` 引用；**再加** `~/.dsh/llm-deepseek/files-v3.json`
  里出现过的 `attachmentId`（远端登记仍指向它，不 mark 就会删掉仍被引用的对象，§13-⑦）。
- **不可判定持有者**：任何"像会话但读不出头"的目录 → **整次 gc 中止**。
- **草稿/在途**：上传后还没进日志的附件只存在于客户端草稿里，服务端无法枚举 →
  用**宽限期**兜底：只回收 `mtime` 早于 `graceDays`（默认 7）的对象。
- **staging 里的日志不算根**：它们对应的会话已被提交删除，其引用不该让对象继续存活。

gc 自身的预写清单、校验、审计与 delete 同构。

## 7. 事后校验与审计

### 7.1 校验

1. `persistence.list()` 不含该 id；
2. 检查点文件不存在——而且要**分两次读**：settle 删完之后、以及静置窗口结束后各读一次。
   因为 `detach()` 触发的 dispose 是**异步**的，它可能在第一次校验之后才写完检查点（§14-A1）；
3. 每个 workspace 的 `sessionIds`、`registry.archivedSessionIds`、`registry.pinnedSessionIds` 都不含它
   —— 这三个集合 0.2.1 都**可读**（`get archivedSessionIds` / `get pinnedSessionIds`）；
4. `entries/` 已清空。

**校验只断言它读得到的东西。** 读不到的（例如某个域的服务没挂载）必须写成
`unverified: [<域>]` 并计入 `outcome: verified-with-gaps`，不许静默算通过（§13-⑧）。

### 7.2 审计

`<DSH_HOME>/session-purge/audit.jsonl`，只追加，每条含 runId、目标、字节数、每步结果、校验结论、
`unverified` 列表。**上限 8 MiB，超了滚动成 `audit.1.jsonl`**（§13-⑨）。

## 8. 失败分类与稳定错误码

| 码 | 触发 | 副作用 | 状态 |
|---|---|---|---|
| `session-unknown` | 索引里没有 | 无 | 未提交 |
| `caller-session` | 目标是发起调用的会话 | 无 | 未提交（§13-⑩） |
| `live-unstoppable` | 复检仍有 activity | 已还原 prior | 未提交 |
| `foreign-writer` | flock 争用（仅 POSIX） | 已还原 prior | 未提交 |
| `linked-shared` | 两个会话链接同一目标 | 无 | 未提交 |
| `cross-device` | EXDEV | 已还原 prior | 未提交 |
| `busy` | 另一个 run 在跑 | 无 | 未提交 |
| `commit-failed` | `rename` 失败（含 Windows 句柄占用） | 部分目标已提交 | **需恢复** |
| `verify-failed` | 提交后校验不过 | 已提交 | **需修复**，附差异 |

最后两条必须诚实标注"已提交"。

## 9. 验证计划

| 不变量 | 注入 | 断言 |
|---|---|---|
| I1 | commit 各 rename 之间崩溃 | 任一时刻 `list()` 不含半状态 |
| I2 | 工作区摘除失败 | 回滚到操作前 |
| I3 | 损坏日志 + 共享对象 + 跑 gc | gc 中止，一字节不删 |
| I4 | 驱逐后立刻读检查点 | 不存在 |
| I5 | 伪造"清单 + 部分条目" | 一次启动后收敛 |
| I6 | 校验读到残留 | `outcome: failed` + 审计 |
| **I7** | **fence 后取消，会话原本 pinned** | **置顶回来、归档位回到 false** |
| **恢复防误删** | **提交后把同名目录换成内容不同的目录，再触发恢复** | **不删（identity 不一致 → `identity-drift`）** |
| A1 | staging 指到另一设备 | 拒绝、无变化 |
| A2 | 子进程持 flock | 拒绝、无变化 |
| A3 | 附件有远端副本 | 报告点名 |

## 10. 回收站（拿掉约束后的结论）

不加。理由不是"用户不让"：**归档已经是可撤销的删除**；回收站 = 归档 + 延迟销毁，是第二套状态机；
而且它制造"已删"的隐私假象——比删错更糟。

若要撤销窗口，正确形态是 `retainMinutes`（默认 0）+ `restore(runId)` + UI 明示"尚未释放"。

---

## 11. 竞品取舍

- **吸收**：`stopActivity` 停活、驱逐后防写回、链接布局分策略（Baboo 六种布局实测）。
- **不吸收**：回收站、直接重写 `workspace.json`、工作区级删除。
- **增量**：预写清单、全局互斥、启动即恢复、校验 + 审计、跨进程围栏、GC 分离。

---

## 12. 一句话

> **删除 = 一次有身份、有提交点、有围栏、有补偿、有校验、有留痕的事务；共享字节不在这里动。**

## 13. 自审：v2 的五处真问题

| # | 问题 | 严重度 | v3 的修法 |
|---|---|---|---|
| ① | **§4.2 仍让 prepare 计算附件可达性**，而 §6 说删除绝不碰附件——自相矛盾 | 中 | prepare 不再算，`steps` 里删掉 attachments |
| ② | **`stopActivity` 吞掉所有 provider 失败**（源码：`try/catch` + `logger.warn`），所以 `live-unstoppable` 永远不可能触发 | **高**（错误码是死码） | fence 增加"静置后复检 activity" |
| ③ | §4.2 说检查点"删两次"，但驱逐在提交**之前**，第二次没有对象 | 低 | 改为删一次 + 校验时再读 |
| ④ | 全局互斥锁在 staging 根上，两份配置不同 staging、同一 sessions 根时不互斥 | 中 | 锁键改为 `realpath(sessionsRoot)` 派生 |
| ⑤ | §4.4 说"收敛"，但 commit 中途崩溃必然留下"部分删、部分留" | 中 | 明确批量语义是最终一致，并要求报告逐条说明 |
| ⑥ | §5.2 没考虑**两个会话链接到同一目标**——删一个会带走另一个的字节 | **高**（别名危险） | prepare 对 `realTarget` 去重，冲突即拒绝 |
| ⑦ | §6 的 gc 没把 `llm-deepseek/files-v3.json` 的 `attachmentId` 当根 | **高**（会删掉仍被远端登记引用的对象） | 加入根集合；并加 7 天宽限期兜住客户端草稿 |
| ⑧ | §7.1 的校验没交代"读不到的域怎么办" | 中 | 引入 `verified-with-gaps` + `unverified` 列表 |
| ⑨ | 审计无上限 | 低 | 8 MiB 滚动 |
| ⑩ | 没有拒绝"删除发起方自己的会话" | 中 | `caller-session` 码 |
| ⑪ | 复检/已归档分支依赖 `workspace/session-activity`、`workspace/session-stop` 两个**事件名**（别的包的内部契约） | 中 | 优先走服务；事件调用包 try/catch，拿不到就记 `unverified` 并按保守处理 |

**还有一条不是 bug 但必须写明的事实**：`archiveSession` 对**已归档**的 id 直接 `return`（源码第一行就 return），
所以已归档会话根本不会收到 stop；v3 因此对这种情况显式改走 `workspace/session-stop` 事件。

## 14. 外部审计（2026-10-18）后的修订

把 v3 交给另一个模型做敌对审计，它给了五条「致命问题」。逐条对照本系统后：**吸收四条，驳回一条（架构上做不到），修正两处措辞。**

### 14.1 采纳

**A1（最有用）复活竞态：校验可能通过，而写入还没结束。** 它给的时序是：

```
evict → dispose 异步写检查点 → rename → settle 删检查点 → dispose 写入完成
      → verify 看见「没有」 → 下次启动重放又出现
```

我原设计把「驱逐」放在提交前就以为安全了——**错在 dispose 是异步的**。修法三件：
① `await` 驱逐返回的 promise；② settle 删完之后**再静置一次并复读**；③ verify 的检查点断言分两次读。

**A2 fsync 目录项。** 文件内容 fsync ≠ 目录项落盘。`rename` 之后必须 fsync **源与目标两个父目录**。

**A4 I7 是自欺。** `stopActivity` 中断的工作还不回来；补偿 `unarchive→pin` 也可能覆盖这期间用户的合法操作。
把 I7 降级为「可补偿（有界）」，并把「补偿可能漂移」写进审计与错误码。

**A5 域外残影。** 被引用会话的完整转录会以 `session-reference-N.txt` 存进**引用方的 spill**。
删掉 A，B 里仍有 A 的全文，直到 B 的 spill 过期（30 天）。这不是「会话复活」，但确实是数据残留——
必须在「删什么 / 不删什么」里写明，不能让用户以为删干净了。

### 14.2 驳回：DeleteGroup + 全局墓碑

它主张把提交点从 rename 移到一条**所有读取路径都遵守**的权威删除记录（墓碑），这样逻辑删除才是原子的。
**这个方案在这个部署里做不到**：插件改不了 `persistence.list()`、workspace 视图、schedule 读取、搜索接口的代码。
一条它们不看一眼的墓碑不是提交点。要真做到，得由上游在持久化层提供 `delete`（这正是上游拒绝做的事）。

**但它的批评有一半是对的**：我的「I1 原子可见性」承诺过大——多域之间不可能在同一瞬间消失。
所以 I1 限定为：**单个域内原子；跨域以「完成后一致」为准，并由 verify 证明「完成后」。**

### 14.3 修正措辞

- **「提交点」→「命名空间提交点」**：rename 只对会话目录这一个域提交，别让读者以为它提交了七个域。
- **「最终一致」要写清方向**：崩溃后**只能向前**（已提交的必须删完），不能因为某个域失败就把会话放回来。

### 14.4 它说对、但我们只能保守处理的

- **链接不能用 basename 判归属**，要用 realpath + 设备/inode 身份；共享目标不必整批拒绝，
  走「只删会话文件」的保守分支即可（§5.2 有一条，我保留「拒绝」作为更保守的默认）。
- **父子批量**：真正安全的做法是「目标集绑成一条逻辑事务」，同样需要上游支持；
  我们能做的是：manifest 绑定整组、恢复只向前、并且**同组目标在 fence 阶段一次性停止**。

## 15. 第二轮：它撤回了墓碑，但留下一条必须接住的义务

我把「服务不可替换」的证据发了过去（`provide` 冲突直接抛错、两条读取路径都在别的包里）。它的回应：

> 我撤回一个隐含前提：不能把全局墓碑 / DeleteGroup 当成你当前部署里可直接实施的方案。
> 但**你可以把 I1 明确降级为单域内原子、跨域最终一致**；verify 能证明「某次验证时各域已达标」，
> **不能**证明跨域曾经原子切换，也不能独自证明未来不会有迟到写入再次制造残影。
> 因此我接受这个约束下的目标，但会继续审查：**你的恢复协议能否确保已提交目标不会被错误恢复、迟到写入或外部状态变化破坏。**

这条我接。它指向一个我原来没写死的点：**恢复只按 id 认人**。已提交（已 rename 进 staging）的目标
如果在恢复前被外部改写（从备份拷回同名目录、同 id 被重新创建），按 id 恢复就会删掉**新的**那个。
所以加了「恢复先验 `identity`，不一致就 `identity-drift` 跳过」。

迟到写入、外部变化分别由双次读取（§4.2）与校验（§7）覆盖；**不声称它们被"证明"，只说被"检测"**。
这也是双方一致的结论：拿不到上游写屏障时，能做到的上限是「检测 + 只向前」，不是「证明不存在」。
