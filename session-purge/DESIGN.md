# 设计 v2：会话删除

> v1 交出去之后，我按要求把"操作者的约束"全部拿掉重做了一遍（不停在"不留回收站"上，也不停在"不重启"上）。
> 结论先说：**"不留回收站"不是妥协，而是这个系统里唯一自洽的选择**；但 v1 有四处不够严谨，v2 补上——
> 预写清单、全局互斥、启动即恢复、事后校验；以及一处结构性错误：**附件回收不该挂在删除上**。

---

## 1. 删除在只追加系统里的含义

dsh 的会话日志是只追加的，`seam 无删除接口`。所以"删一个会话"实际上是：

> **撤销一份权威，并让所有派生在有限步内收敛到没有它。**

它不是文件操作，是一次**跨域的可达性回收**。这条定义决定了后面所有东西：判断一个字节该不该删，问的不是"它叫什么名字"，而是"还有没有权威引用它"。

---

## 2. 正确性模型

### 2.1 不变量

| # | 不变量 | 形式化 | 违反的例子 |
|---|---|---|---|
| **I1** | **原子可见性** | 任一观察者在任一瞬间，该会话要么完整存在，要么完全不存在 | `rm -rf` 删到一半 |
| **I2** | **无悬空权威** | 提交后，不存在指向它的权威记录（记账/提醒/归档集合） | 行还在、点开报错 |
| **I3** | **无共享伤害** | 其他会话仍引用的字节，必须完好 | 删 A 把 B 的图片带走 |
| **I4** | **不可复活** | 提交后没有任何路径能重建它的记录 | dispose 写回投影缓存 |
| **I5** | **收敛** | 崩溃/失败后，再跑一次（或启动时）达到 I1 满足的状态 | 半删的目录永远留着 |
| **I6** | **可证伪** | 每次删除结束后都要**校验**，而不是假设 | 报告"成功"但磁盘还在 |

### 2.2 假设（写清楚，才能谈绝对）

| # | 假设 | 不成立时的行为 |
|---|---|---|
| **A1** | 会话根与 staging 父目录在**同一设备** | `rename` 抛 `EXDEV` → 拒绝整批，不降级 |
| **A2** | POSIX 上 `flock` 可用；Windows 无锁文件 | POSIX 用租约证明互斥；Windows 退化为"`rename` 失败即拒绝" |
| **A3** | 远端已上传文件由提供方过期回收 | 本地删字节后远端副本残留，**在报告里点名** |

### 2.3 可证明不可达的目标

不说"绝对安全"，说清楚**哪三件事做不到**：

1. **跨卷原子提交**：目标在另一设备时没有原子动作，只能拒绝。
2. **Windows 的跨进程写者**：仲裁者是命名内核信号量，插件拿不到；只能靠 `rename` 失败来拒绝。
3. **远端副本**：`files-v3.json` 的 `fileId` 在对方服务器上，删不了，只能等过期。

**"绝对"在这里的正确含义是：所有失败模式都被枚举、每一种都有确定行为、每一种都有测试。** 不是"不会出问题"。

## 3. 域与所有权

### 3.1 七个域

| 域 | 性质 | 权限 | 处置 |
|---|---|---|---|
| 会话目录（日志+锁） | **权威** | 独占 | 提交点：移出树 |
| 投影检查点 | 派生 | 可写 | 删；**驱逐后要再删一次** |
| 工作区记账（成员/归档/置顶） | **权威** | 共享 | 走注册表服务 |
| 提醒 | **权威** | 共享 | 走 Schedule 服务 |
| 附件字节 | **共享权威** | 共享 | **不在这里删**（见 §6） |
| 搜索索引 | 派生 | 只读 | 不碰（自对账） |
| spill / 引用副本 / 临时对象 | 临时 | 独占 | 顺手删；有 30 天自清扫兜底 |

### 3.2 谁有权删：停 → 静置 → 驱逐 → 围栏

1. **停**：`archiveSession(id, {stopActivity: true})`。官方缝，先写归档集合再发停止请求，覆盖 agent/job/subagent/schedule 四种"活"。
2. **静置**：给收尾一个窗口，让最末的 `turn/end` 落盘。
3. **驱逐**：`sessions.store.get(id)?.detach?.()`，否则 Windows 上写句柄挂到进程退出、POSIX 上 dispose 会把检查点写回来。
4. **围栏**：POSIX 取 `session.lock` 的 `flock`（`r+` + inode 校验），证明没有别的进程在写。

**顺序不可交换。** 拒绝是最后手段，不是第一手段。

## 4. 状态机与预写清单

### 4.1 为什么需要清单，而不是"目录即日志"

v1 说"staging 里的目录就是这次删除的记录"。不够严谨：目录只能证明"有东西被移出来了"，证明不了**是谁移的、移到哪一步了、附件怎么处理**。任何往 staging 里丢垃圾的人都会让恢复逻辑去删他不知道的东西。

所以 v2 用**预写清单**（WAL）：提交点之前先写 `manifest.json`，它才是这次事务的身份。

```
<stagingRoot>/<runId>/
  manifest.json          # 意图、目标、每步进度、结果
  entries/<project>/<sessionDir>/   # 被移出的真实目录
```

`manifest.json` 写入方式：`write tmp → fsync → rename`（原子），字段：

```json
{
  "version": 1,
  "runId": "20261018T183700-3f9a",
  "startedAt": 1792345678901,
  "caller": "ui",
  "targets": [{ "id": "session-…", "projectDir": "--…--", "dirName": "session-…",
                "identity": "dev:ino", "sizeBytes": 12345, "linked": false }],
  "steps": { "fence": "done", "commit": "partial", "workspace": "pending",
             "cache": "pending", "schedules": "pending", "attachments": "skipped" },
  "outcome": null
}
```

**恢复只认清单里的 runId 目录**；没有清单的目录一律不动、只在报告里记为"未知残骸"。（v1 的"目录即日志"会把无名残骸也删掉，那是过度自信。）

### 4.2 run 的生命周期

| 阶段 | 动作 | 写盘 | 清单进度 |
|---|---|---|---|
| **prepare** | 索引、算目标集、算血缘、查活、**算附件可达性**（只在开启时） | 清单 | `steps={}` |
| **fence** | 停 → 静置 → 驱逐 → 取租约（整批） | — | `fence: done` |
| **commit** | `rename` 每个目标到 `entries/` | 是 | `commit: partial→done` |
| **settle** | 撤销：工作区 → 检查点（删两次：提交后一次、驱逐后再一次） → 提醒 | 是 | 逐步 `done` |
| **cleanup** | `rm -rf entries/`；`manifest.outcome` | 是 | `cleanup: done` |
| **verify** | 事后校验（§7） | 审计 | `outcome: verified/failed` |

### 4.3 全局互斥

同一 `$DSH_HOME` 同时只允许**一个** run：

```
flock(<stagingRoot>/.lock, LOCK_EX | LOCK_NB)  # 拿不到 → 拒绝：另一次删除正在进行
```

理由：两次 run 交错会互相覆盖 `entries/`，而恢复逻辑按 runId 收敛——并发 run 会让"谁删了谁"不可判定。这条 v1 漏了。

### 4.4 崩溃矩阵

| 崩在 | 磁盘 | 外界可见 | 恢复动作（启动时自动执行一次） |
|---|---|---|---|
| prepare | 只有清单 | 完整 | 删清单目录（还没提交） |
| fence | 只有清单 | 完整 | 删清单目录；租约随进程消亡 |
| commit 中 | 清单 + 部分条目 | 已提交的不见了，其余正常 | 对每条目重做 settle → cleanup → verify |
| settle 中 | 全部在 entries/ | 都不见了 | 重做剩余步骤（全部幂等） |
| cleanup 中 | entries/ 残片 | 都不见了 | 直接删残片 |
| verify 后崩溃 | 清单未标 outcome | 都不见了 | 重跑 verify；不一致则记审计 |

**恢复在启动时自动跑一次**（v1 是"下次操作时"，可能几天都不发生，磁盘一直脏着）。

## 5. 提交点

### 5.1 普通目录：`rename` 出树

`<sessions>/<proj>/<dir>` → `<staging>/<runId>/entries/<proj>/<dir>`。同设备，原子；此后 `list()` 不可能看见它。

### 5.2 链接目录：`rename` **链接本身**

v1 说"链接布局没有提交点"——**错了**。链接是会话根里的一个目录项，`rename` 它同样是原子的，而且同样让 `list()` 立刻看不见它。区别只在 cleanup 阶段：

- 目标是宿主布局（目标名 == 会话 id）→ 递归删目标，再删链接（链接在 `entries/` 里，本身就是"已提交"的凭据）；
- 目标名任意 → **只删目标里的会话文件**（`session*.jsonl*`、`session.lock`），`rmdir` 变空才成功，其余保留并写进 `leftover`；
- 目标里没有任何会话文件 → 拒绝（在 commit 之前就拒绝，避免把链接移走却删不了负载）。

**提交点因此对所有布局成立**；只有"目标字节的原子回收"做不到——那本来就不是原子操作。

配套的索引修正（否则这类会话根本不会出现在列表里）：`indexStoredSessions` 现在只认
`dirent.isDirectory()`，而链接的 dirent 报的是 `isSymbolicLink()`。要让它可见，索引必须
`lstat` 后按"解析目标是否为目录"归类，并在记录里带上 `linked: true` 与 `realTarget`——否则
预览里没法说清"这次会连同另一块盘上的目录一起删"。

### 5.3 `EXDEV`

拒绝整批，报告里说明"会话根与事务目录不在同一设备"。**不降级为就地 `rm -rf`**——那等于放弃 I1。

## 6. 共享字节：把 GC 从删除里拆出去

v1 把附件回收挂在删除上（可选的引用减法）。**这是结构性错误**，理由三条：

1. **正确性依赖目标集**：删一个会话要扫全部日志，删十个就扫十遍，且"哪些对象还能删"取决于这一次删了什么——这让一个本该全局的判断变得局部、易错。
2. **可达性不可证**：不可读日志引用着的对象，任何一次局部扫描都看不见（我们已经踩过一次）。
3. **上游立场一致**：附件域明确把 GC 推迟了，因为"恢复和 fork 的会话可能共享不可变对象"。硬塞进删除里，是在别人没决定 GC 语义前替它做决定。

**v2 的拆法：**

- **delete**：只删会话自己的权威，**绝不碰附件**。因此 I3 从"要靠算法保证"变成"结构性不可能违反"。
- **gc**（独立操作，像 `git gc`）：全量 mark-and-sweep——
  mark：遍历**所有**权威日志里出现的 `sha256:` 引用（含不可读目录 → 直接中止，报"不可判定持有者"）；
  sweep：删除未被 mark 的对象与链接；
  gc 自身也走预写清单 + 校验 + 审计。

代价：删除不再顺带清字节。收益：删除的正确性不再依赖任何跨会话推理。

## 7. 事后校验与审计

### 7.1 校验（I6）

commit 之后逐条断言：

1. `persistence.list()` 里没有该 id；
2. 投影检查点不存在（**驱逐后再查一次**，防 dispose 写回）；
3. 每个 workspace 的 `sessionIds` 与归档/置顶集合都不含它；
4. `entries/` 里该条目已清空；
5. 失败则 `outcome: failed`，并把差异写进审计——**绝不因为"我们本来以为成功了"就报成功**。

### 7.2 审计

每次 run 追加一行 JSON 到 `<DSH_HOME>/session-purge/audit.jsonl`：时间、runId、目标、字节数、每一步结果、校验结论。只追加、只写自己目录、可被用户直接读。

理由：这个操作是破坏性的，事后必须能回答"它到底做了什么"。这一条没有任何竞品做，而它几乎零成本。

## 8. 失败分类与稳定错误码

| 码 | 含义 | 用户看到 | 状态 |
|---|---|---|---|
| `session-purge/session-unknown` | 索引里没有 | 会话不存在 | 无变化 |
| `session-purge/live-unstoppable` | 停不下来（provider 拒绝/超时） | 请重试 | 无变化 |
| `session-purge/foreign-writer` | 别的进程持锁 | 请关闭另一个窗口 | 无变化 |
| `session-purge/cross-device` | EXDEV | 说明原因 | 无变化 |
| `session-purge/busy` | 另一个 run 在跑 | 稍后再试 | 无变化 |
| `session-purge/linked-unresolvable` | 链接目标不可删 | 说明原因 | 无变化 |
| `session-purge/verify-failed` | 提交后校验不过 | 附差异 | **已提交**，需修复 |

前六条都发生在提交点之前——所以它们的共同语义是**什么都没发生**。最后一条发生在提交之后，必须诚实标注。

## 9. 验证计划：故障注入矩阵

| 不变量 | 注入方式 | 断言 |
|---|---|---|
| I1 | 在 commit 的每条 rename 之间注入崩溃 | 任一时刻 `list()` 不含半状态 |
| I2 | 人为让工作区摘除失败 | 回滚到"什么都没发生" |
| I3 | 造一个损坏日志引用同一对象 + 跑 gc | gc 中止、一个字节都没删 |
| I4 | 驱逐后立刻检查检查点 | 不存在（再删一次生效） |
| I5 | 伪造"清单 + 部分条目"的现场 | 一次启动后全部收敛 |
| I6 | 人为让校验读到残留 | `outcome: failed` + 审计留痕 |
| A1 | 把 staging 指到另一设备 | 拒绝、无变化 |
| A2 | 子进程持 flock | 拒绝、无变化 |
| A3 | 附件有远端副本 | 报告点名"远端仍存在" |

## 10. 关于回收站（拿掉约束后的结论）

我认真考虑过加回收站，最后**仍然不加**，理由不是"用户不让"，而是三条工程判断：

1. **产品已经有一个"可撤销的删除"，它叫归档。** 回收站 = 归档 + 延迟销毁，是同一件事的第二套状态机。
2. **回收站制造隐私假象**：用户点"删除"的动机往往是"这东西不该留在磁盘上"。放进回收站 = 告诉他已经删了，其实还在——这是**比删错更糟**的失败。
3. **它引入第二套不变量**：保留期、清扫、恢复、以及"回收站里的东西算不算存在"。每一条都要独立正确，才能不比"直接删"更差。

**如果**将来确实要撤销窗口，正确的做法不是回收站，而是：

- `retainMinutes`（默认 0）：commit 后 entries/ 保留 N 分钟再 cleanup；
- 期间提供 `restore(runId)`：把目录原样移回并重新挂账（走注册表服务）；
- 校验步骤把"仍在 entries/"记为 `outcome: retained`，**UI 必须显示"尚未释放"**——绝不假装删掉了。

也就是说：**可选的延迟，而不是默认的假象。**

---

## 11. 与竞品的取舍（保留结论，压缩）

- **吸收**：官方 `stopActivity` 停活（三家独立收敛）、驱逐后再删一次检查点（Baboo 实测修复）、链接布局按目标名分策略（Baboo 六种布局实测）。
- **不吸收**：回收站（理由见 §10）、直接重写 `workspace.json`（版本耦合）、工作区级删除（语义不同）。
- **我们的增量**：预写清单、全局互斥、启动即恢复、事后校验 + 审计、跨进程围栏、GC 与删除分离。

---

## 12. 一句话

> **删除 = 一次有身份（runId）、有提交点（rename）、有围栏（lease）、有校验（verify）、有留痕（audit）的事务；共享字节不在这里动，回收另有其人。**
