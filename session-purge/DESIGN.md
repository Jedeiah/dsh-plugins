# 设计：一次可证明的会话删除

这份文档回答一个问题：**在这个系统里，"正确地把一个会话删掉"到底意味着什么，我们凭什么说做到了。**

dsh 的持久化层是"只追加"的，`seam 无删除接口`（`dsh-session-persistence-jsonl/README.zh.md:167`）。所以删除不是"删一个文件"，而是**跨七个存储域的一次可达性回收**。没有明确的不变量，就只能靠"记得清哪几处"——那正是残次品的来源。

---

## 1. 设计思想

六条原则，后面每个机制都必须能指回其中一条。

| # | 原则 | 判据 / 后果 |
|---|---|---|
| **P1** | **只撤销权威，不动派生。** 每个字节要么是权威，要么可由权威重建 | 判据只有一句：**能不能从别处重建**。能重建的，删掉或留着都行；不能的，才必须精确处理 |
| **P2** | **一次删除只有一个提交点。** 提交点之前什么都没发生，提交点之后只剩清理 | 提交点是**目录离开 `sessions/` 的那一次 `rename`**。它之后任何崩溃都不会让外界看到半删状态 |
| **P3** | **删者持锁。** 所有权由内核裁定，不由我们猜 | 拿不到租约就不删。宁可让用户重试，也不在别人正写着的时候动刀 |
| **P4** | **引用从宽，独占从严。** 共享字节只删"可达性可证为空"的那部分 | 证不出来就不删。**宁可泄漏，不可误删**——泄漏可以再收，误删收不回来 |
| **P5** | **失败二值化。** 任何一步失败，要么回到删除前，要么推进到删除后 | 不允许"停在中间"：没有半删的目录、没有留下槽位的孤儿 |
| **P6** | **不碰别人的格式。** 只调用服务，或整文件删除 | 绝不解析、不改写别的域的结构化文件（`workspace.json`、`schedule.json`、索引库） |

一句话概括：**删除是一次事务，提交点是命名空间里的一个 `rename`。**

---

## 2. 域地图与处置

七个域，处置方式由 P1 直接推出。

| 域 | 位置 | 性质 | 动作 | 失败后果 |
|---|---|---|---|---|
| 会话日志 + `session.lock` | `sessions/<proj>/<id>/` | **权威** | 提交点：`rename` 出树，再 `rm` | 未提交则原样；已提交则只剩清理 |
| 投影检查点 | `storages/session_projcache/<id>.json` | 派生（可由日志重放） | 删 | 残留一条过期行 |
| 工作区记账 | `storages/workspace.json` | **权威**（分组/归档/置顶） | 走注册表方法摘除 | 列表里多一行已失效的 id |
| 提醒 | `storages/schedule.json` | **权威**（绑 `sessionId`） | 走 Schedule 服务删 | 对着不存在的日志触发 |
| 附件字节 | `attachments/v1/{objects,file-objects}` | **共享权威**（内容寻址、跨会话去重） | 仅当 P4 可证时删 | 别的会话图片读不出来 |
| 全文索引 | `session-search.db` | 派生 | **不碰** | 下次搜索前自对账 |
| spill / 引用副本 / 临时对象 | `$TMPDIR/dsh-spill-*` | 临时（`cleanupPeriodDays: 30`） | 顺手删 | 30 天后自己没了 |

`dsh-goal` 不落盘（goal 存在日志里）、`dsh-session-reference` 把转录拷进**引用方自己的** spill、`dsh-workspace-changes` 的 `GIT_OBJECT_DIRECTORY` 在 `mkdtemp(workspace.scratch)` 里——这三处都不需要单独处理，原因都是 P1：**它们要么随日志消失，要么本来就不在会话的域里。**

## 3. 提交点协议

### 3.1 为什么 `rename` 是提交点

- **原子**：同一文件系统内 `rename(2)` 要么完成要么没发生，没有中间态。
- **零内容改动**：从这一刻起 `list()` 看不到它，而字节一个都没动——后面才是可以慢慢来、失败了也能重来的一步。
- **同卷**：staging 放在 `dirname(sessionsRoot)` 下（默认就是 `$DSH_HOME`），与 `sessions/` 同卷，保证不是 `EXDEV`。
- **`EXDEV` 不降级**：换成"就地 `rm -rf`"就等于放弃 P2。跨卷时直接拒绝并说明原因。

### 3.2 staging 在哪、为什么不能放在会话树里

后端是这么枚举的：

> `listProjectDirs`：`entries.filter((e) => e.isDirectory())` —— **根下每个目录都算项目目录**，没有点号过滤、没有命名形状检验。
> `listSessionDirs`：项目目录里出现散落的 `*.jsonl` 会直接抛 `legacyLayout`。

所以在 `sessions/` 里放任何 staging 目录都会被当成项目、把已提交的会话重新列出来。**staging 必须在会话树之外**：

```
$DSH_HOME/.session-purge-staging/<runId>/<projectDir>/<sessionDir>/
```

### 3.3 staging 不是回收站

- **无保留期**：本次操作的最后一阶段就 `rm` 掉。
- **不承诺可恢复**：留下的残骸在下一次操作开始时被无条件清扫，不做提示、不提供还原。
- 它存在的唯一理由是 P2——把"一次性不可分割的提交"落到一个能原子完成的动作上。**卸载/停用插件不需要清理它**：下次任何一次删除都会顺手扫掉。

### 3.4 阶段

| 阶段 | 做什么 | 写盘 | 失败时 |
|---|---|---|---|
| **P0 判定** | 索引、算目标集（血缘/分叉）、算附件可达性、查活 | 否 | 什么都不变 |
| **P1 取锁** | 对每个目标取写租约（见 §4） | 只碰 `session.lock` | 整批放弃，什么都不变 |
| **P2 提交** | 逐个 `rename` 进 staging | 是 | 已提交的继续、未提交的原样；恢复见 §5 |
| **P3 撤销** | 工作区槽位/归档/置顶、投影检查点、提醒、附件 | 是 | 已提交的目标继续走恢复流程 |
| **P4 清理** | `rm -rf` staging 条目；顺带清扫历史遗留 | 是 | 下次再扫 |
| **P5 收尾** | 释放租约、广播 `api-session/removed` | 否 | 广播失败只影响 UI，下次列表自然刷新 |

**顺序上的两个硬约束：**

1. **P2 必须在 P3 之前**：投影检查点和附件可达性都要读日志，日志一旦进 staging 就只剩那一处副本。
2. **附件 digest 在 P0 算、P2 之后才删**：算法需要"被删集合"和"存活集合"的**全部可读日志**；提交后日志已不在原处，只能靠 staging 里的副本重算（§6）。

## 4. 租约：谁有权删

dsh 的写租约是对进程可见的：

> POSIX：`session.lock` 上的非阻塞 `flock(2)`；争用映射为 `SessionAlreadyOwnedError`；**拿到锁后要校验 inode 仍是该路径**（防 unlink-recreate），重试三次。
> Windows：由路径派生的命名内核信号量，**没有锁文件**。

于是：

| 平台 | 手段 | 强度 |
|---|---|---|
| POSIX | `open('r+')` + `tryLockExclusive(fd)` + inode 校验 | **可证明**：我们持锁时，后端的写打开必然拿到 `SessionAlreadyOwnedError`，最后一次检查点写不出来（这正是"活会话删除会复活缓存"的根因） |
| Windows | 拿不到信号量；**但 `rename` 本身就是排他测试** | 有别的进程持有句柄且未授权 delete 时，`rename` 失败（`EBUSY`/`EPERM`）。**拒绝**，而不是排队 |

关键点：**提交步骤在所有平台同时充当排他测试**。POSIX 上租约让它更早、更明确；Windows 上它是唯一可用的判据。因此"单实例前提"这条免责不再需要——我们不再依赖它。

进程内注册表（`agents`/`sessions`）仍是第一道闸：它是**同一进程里更快、更明确的拒绝**，不是唯一保障。

## 5. 崩溃矩阵

staging 里每个 `<runId>/<project>/<id>` 就是"这次删除**已提交**、尚未清理"的记录——**目录本身就是日志**，不需要额外的 journal 文件，也就没有"日志与状态不一致"的问题。

| 崩在 | 磁盘状态 | 外界可见 | 下次操作的收敛 |
|---|---|---|---|
| P0/P1 | 什么都没变 | 完整 | 无需动作（锁随进程消亡） |
| P2 之中 | 一部分在 staging，一部分在原位 | 已提交的不见了，其余正常 | 对 staging 每条：重做 P3 → P4 |
| P3 之中 | 全部在 staging，派生域处理了一半 | 都不见了 | 同上（P3 幂等：摘槽位、删行、删提醒都可重复） |
| P4 之中 | staging 里可能只剩残片 | 都不见了 | 直接 `rm` 掉残片 |

**恢复的触发点**：任何一次 `purge` 开始时、以及 `sweepResidue` 扫描时。恢复不需要用户参与，因为 staging 里的东西**已经**从 UI 消失，收尾只是清理。

---

## 6. 附件：可达性怎么算才叫"可证"

附件是**内容寻址、跨会话去重**的，上游明确把 GC 推迟了：

> `dsh-attachment-local`：已存储的图片永远不会被自动删除，**也没有任何机制回收未被引用的对象**……理由是恢复和 fork 后的会话可能共享不可变对象。

所以我们只能做"删除时的一次性引用减法"，而它的**正确性完全取决于扫描范围**：

- **domed**：目标集的日志（P0 时仍可读）。
- **surviving**：索引里所有非目标会话的日志。
- **不可读的会话目录 = 不可判定的持有者**。它不在索引里（后端 `list()` 也跳过它），但它的日志可能引用着某个对象。**只要存在一个这样的目录，整批附件删除就放弃**，并写进 `warnings`。
  这条是 P4 的直接推论：证不出来就不删。
- **远端副本**：`~/.dsh/llm-deepseek/files-v3.json` 里的 `fileId` 是对方服务器上的对象，本地删字节它不会消失，只能等 `expiresAt`。**明确声明为域外残留**，不假装清掉了。
- **代价**：扫描是 O(总日志字节)，超限就拒绝（现有行为），不做"尽力而为"的近似。

## 7. 不变量 → 机制 → 测试

| 不变量 | 机制 | 怎么测 |
|---|---|---|
| **C1 原子性** | P2 的 `rename`；staging 在树外 | 提交后：源路径不存在、staging 里是完整树；中间态不可构造（`rename` 无中间态） |
| **C2 无悬空权威** | P3 走服务方法；失败挂回槽位 | `chmod 0o500` 造"删不掉"：断言槽位回来、检查点还在 |
| **C3 无别名伤害** | 引用减法 + opaque 持有者拒删 | 造一个损坏日志的会话引用同一对象：断言附件一个都不少、有 warning |
| **C4 不可复活** | P1 持租约（POSIX）/ `rename` 排他（Windows） | 子进程持 flock → 断言拒绝；持锁期间后端写打开必然失败 |
| **C5 幂等/崩溃收敛** | staging 即日志；恢复 = 重做 P3 + P4 | 构造"只有 staging 条目、派生域未清"的现场 → 断言一次操作后全部收敛 |
| **P5 失败二值化** | 每步只有"回滚"或"推进"两种出口 | 扫描中途取消：断言未提交的目标原样、已提交的收敛 |

## 8. 与现状的差异

**保留**：索引/血缘/fork 判定、目标集漂移拒删、`inspect` 预览、残留扫描（扩到"孤儿派生行"）、`sweepResidue` 的两道收窄。

**替换**：

1. `removeSessionDirectories` 拆成 `commitTargets`（rename）与 `cleanupStaging`（rm）。
2. 删除顺序改为：取锁 → rename → 撤销 → 清理 → 释放 → 广播。
3. 新增 `recoverStaging()`：每次操作开头先收敛上一次的残局。
4. 附件增加 opaque 持有者检测（有就整批放弃）。
5. 移除"失败后靠 `rm` 重试"的路径——失败只发生在 P2 之前（什么都没变）或 P3/P4（已提交，靠恢复收尾）。

**明确不做**：回收站/撤销；解析或改写别的域的文件；通用附件 GC；Windows 多实例"排队"（只能拒绝）；`EXDEV` 下的降级删除。

---

## 9. 一句话

> **删除的语义不是"把文件抹掉"，而是"撤销这份权威，并让所有派生在有限步内收敛到没有它"。**
> 提交点是那一次 `rename`；在此之前的失败什么都没发生，在此之后的失败只是清理。附件只在"能证明没人用"时才删——证不出来就留着，因为泄漏可以再收，误删收不回来。
